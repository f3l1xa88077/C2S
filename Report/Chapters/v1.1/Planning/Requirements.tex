The compiled requirements focus on the sub-systems, as the system requirements were collated into the Phase B CubeSat work package. Unliked v1, system specifications were developed alongside the rationale as the design considerations were already imposed from previous versions or existing standards. The following requirements and specifications were compiled in \autoref{tab:v1.1-requirements}.

\subsubsubsection{Camera}

\requirement{JPEG Codec}
{Hardware accelerated JPEG compression on the STM32 is much faster than by software, meaning the chip is running for less time and less power is consumed.}
{TBD if needed, yet to be tested}

\requirement{Colour Format}
{The images will be captured in RGB and YUV colour format. YUV is required for ICER and JPEG compression, and RGB as a backup for JPEG.}
{Needs to be justified by v1.0 and v0.1 testing. As we are using OV7670: RGB565, RGB555, YUV422}

\requirement{DCMI Camera}
{As the mission requirements are to capture an image, we should aim to do that in the easiest way. Although CSI-2 could give us really good images, DCMI can deliver and that's all we need right now. It's been verified to work on v1.0, so pivoting to a new interface risks needing more versions.}
{Architecture should support images up to 5 MP. According to Phase B requirements, the ouput image must be smaller than $\sim$1.62 MB.}

\requirement{Image Metadata}
{Attaching important information alongside the photo is important for identifying when it was taken, so we can estimate what it is taking a photo of.}
{Request RTC time from OBC and attach to image metadata. Image size, colour space, etc.}

\requirement{OV7670 Camera}
{There is already a functioning driver for the camera. Additionally, we don't currently have the budget for an additional camera module.}
{Same module from v1.}

\subsubsubsection{Memory}

\requirement{High Data Rate External Memory}
{High bandwidth and fast memory is required to rapidly buffer image data, as testing from v1.0 showed that direct CPU writing to QSPI took far too long.}
{Needs to be compatible with FSMC/FMC. Needs to buffer at least the maximum size of expected RAW image data.}

\requirement{High Capacity External memory}
{The internal memory of STM32s are not large enough to store one or more images. An additionaly lower data rate, but higher capacity external memory reduces costs compared to one single large capacity, high data rate extended memory option.}
{Needs to buffer the output of at least 4 images (NEED TO CONFIRM WITH COMMS).}

\requirement{SD Card}
{Allows us to write several images to external, non-volatile memory, where easy data recovery and data integrity is a priority. Very applicable for HAB missions and isolated testing.}
{SDMMC as it worked on v0.1 and is native to the STM32. 4-bit width to ensure writing does not block or halt the processor for longer than necessary.}

\requirement{File Management}
{As large amounts of memory will be moved around, an effective file/memory management system should be implemented to avoid memory overhead. A cleaner memory management reduces the risk of memory leaks or corruption.}
{Dynamic memory allocation and storage. Moving memory between different addresses and keeping track of locations and metadata.}

\subsubsubsection{Power}

\requirement{Current per MHz}
{Reducing this draws the power consumption away from the STM32, what is typically the most power hungry component.}
{As low as reasonably practical.}

\requirement{CSA}
{For board power characterisation.}
{Continue to use the INA219 as worked with v1.}

\requirement{Buck Converter}
{To reduce power loss from LDO directly - 33\% of power was estimated to be from the LDO alone on V1.}
{Should regulate VEPS to 0.3-0.5V above LDO output voltage.}

\requirement{LDO}
{Need to filter noise from the EPS voltage supply.}
{Very low drop-out voltage and high PSSR.}

\subsubsubsection{Interfaces}

\requirement{DCMI}
{The STM32 needs to receive parallel image data on its dedicated DCMI peripheral.}
{Highest bit-width possible. Master clock output as XCLK.}

\requirement{USB-FS}
{Allows images to be output directly to a dashboard during testing to accelerate the programming process.}
{The STM32 needs to operate in device mode. VBUS sensing not required.}

\requirement{EPS}
{Needs to be powered by EPS.}
{Needs to use dedicated and adhere to the 4-pin EPS connector.}

\requirement{OBC}
{Needs to communicate with OBC.}
{Needs to use inverted OBC connector (slave-side).}

\requirement{C2I}
{Standard camera interface should allow different camera modules to be swapped out.}
{Should accommodate C2I 1.0 requirements, with two 3V3 pins should we exchanged for 5V, to allow camera modules requiring voltages like 3V8 to be used.}

\requirement{OBC Connector Fully Connected}
{Allows the UART pins to be configured as GPIOs for miscellaneous use if needed.}
{Connect SPI and UART pins.}

\subsubsubsection{Hardware}

\requirement{HSE}
{For stable clock, no LSE as RTC not used.}
{TCXO for temperature stability.}

\requirement{Less LEDs}
{I found that most LEDs were unused when developing the other boards, as errors would be flagging in the IDE during debug rather than via an LED.}
{Only using strictly required LEDs: 3V3, CD for SD. Use jumpers so they can easily be desoldered to deactivate LEDs, or configure a GPIO pin as the return path (turn on when driven low).}

\subsubsubsection{PCB Layout \& Physical Design}

\requirement{Silkscreen}
{Silkscreens on v1.0 did not print properly as they were on the edge of JLC requirements.}
{Slightly larger silkscreen text.}

\requirement{Non-through hole headers}
{Through holes take up a lot of space as they go through each layer. As they won't be used on the CubeSat version, no point allocating through-hole space for them if they can just be a surface mount component. Frees up space on other layers and allows the board to sit flush on a surface.}
{Surface mount, 0.1 inch.}

\requirement{Mounting holes}
{Needs to be secured to a payload bay and vibration table}
{Must be in a square pattern for FlatSat mounting (according to Mission Manager, Liria S). Standard 4-corner.}

\requirement{Connector Placement}
{External connectors should be placed where we expect the cables to be to reduce cable length and promote organisation and ease of integration.}
{Connectors should be placed on as few sides as possible. The ideal case is a single edge. If connectors are placed on all sides/edges, it effectively expands the actual size of the board, as the new cables sprout outwards from each direction, meaning there's extra cable space / wraparound on each edge.}

\requirement{No BGAs}
{BGA components are no rated for satellites.}
{Selecting packages like LQFP that have stronger solder joints.}

\subsubsubsection{Debugging}

\requirement{SWD}
{For easy programming and live-debugging.}
{No large 20-pin header, 4-pin (SWD, SWCLK, VDD, GND) to reduce PCB size.}

\requirement{Test Points}
{To debug using a logic analyser.}
{Broken out on all signal lines, small test point only e.g., 2mm pad.}

\requirement{Telemetry Logging}
{Shall be capable of relaying heartbeat statuses to OBC to identify and resolve potential issues.}
{Be capable of checking heartbeats upon request and sending results to OBC. Voltage sensing for 3V3 supply.}

\requirement{Remote debugging / control}
{In the event of a fault or error, C2S shall be capable of being restarted or corrected to ensure it operates correctly in the future.}
{Have a circuit or system implemented to automatically reset the STM32 upon a specific OBC command e.g., STM32 activates a scheduler component that activates the RESET pin of the STM32.}

\subsubsubsection{Environmental}

\requirement{Temperature}
{Needs to withstand space environment.}
{Components must have a thermal grade accomodating temperatures of s-40 to 85deg.}
