The compiled requirements focus on the sub-systems, as the system requirements were collated into the Phase B CubeSat work package. Unliked v1, system specifications were developed alongside the rationale as the design considerations were already imposed from previous versions or existing standards. The following requirements and specifications were compiled in \autoref{tab:v1.1-requirements}.

\subsubsubsection{Camera}

\requirement{JPEG Codec}
{Hardware accelerated JPEG compression on the STM32 is much faster than by software. The STM has a co-processor specifically for this, meaning the chip is running for less time and less power is consumed.}
{TBD if needed, yet to be tested}

\requirement{Colour Format}
{The colour format images will be captured in needs to be defined. Different formats take up different amounts of space, sets requirements for memory.}
{Needs to be justified by v1.0 and v0.1 testing. As we are using OV7670: RGB565, RGB555, YUV422}

\requirement{DCMI Camera}
{Avoiding CSI-2. It would open C2S up to really good image sensors, but adding a bridge introduced more complexity. As the mission requirements are to capture an image, we should aim to do that in the easiest way. Although CSI-2 could give us really good images, DCMI can deliver and that's all we need right now. It's been verified to work on v1.0, so pivoting to a new interface risks needing more versions.}
{Architecture should support images around the 2K mark - support, not "must be 2K". According to Phase B requirements, it must be smaller than $\sim$1.62 MB, this just sets the upper limit of the data, not the limit of the resolution. The resolution can be as small or large as possible, just as long as it adheres to the data requirement. For ideal quality, it should be around 2K as this is a sweet spot for resolution and quality.}

\requirement{Image Metadata}
{Attaching important information alongside the photo is important for identifying when it was taken, so we can estimate what it is taking a photo of.}
{Request RTC time from OBC and attach to image metadata. Image size, colour space, etc.}

\requirement{OV7670 Camera}
{Developed working code for the camera module, don't have the budget for an additional camera module.}
{Should have AGC, AWB, AEC properly configured.}

\subsubsubsection{Memory}

\requirement{High Data Rate External Memory}
{High bandwidth and fast memory is required to rapidly buffer image data, as testing from v1.0 showed that direct CPU writing to QSPI took far too long.}
{Needs to be compatible with FSMC/FMC. Needs to buffer at least twice the size of expected RAW image data for sufficient overhead.}

\requirement{Non-volatile external memory}
{As the internal memory of STM32s are not large enough to store one or more images, external memory is required. This must be non-volatile to ensure data is not lost over time e.g., waiting for transmit window.}
{Needs to buffer at least four times the size of the expected RAW memory size for sufficient overhear. One max RAW for the raw image data, another for the compressed image, another for the Comms data, and one for overhead. ..}

\requirement{SD Card}
{Allows us to write several images to external, non-volatile memory, where easy data recovery and data integrity is a priority. Very good for HAB flights and testing.}
{SDMMC. SPI did not work on v1.0. 4-bit wide if possible, 1-bit is the required minimum.}

\requirement{File Management}
{As large amounts of memory will be moved around, an effective file/memory management system should be implemented to avoid memory overhead. A cleaner memory management reduces the risk of memory leaks.}
{Dynamic memory allocation and storage. Moving memory between different addresses and keeping track of locations and metadata.}

\subsubsubsection{Power}

\requirement{Current per MHz}
{Reducing this draws the power consumption away from the STM32, what is typically the most power hungry component.}
{ALARP}

\requirement{CSA}
{For power characterisation}
{Continue to use INA219 as it worked well with v1.}

\requirement{LDO}
{Need to regulate the EPS voltage down to required voltages for operation.}
{Individual supply for the camera and rest of the board. Board can operate in normal noise (acceptable levels). Camera should operate on low noise LDO. Power specifications of the camera mean we can select LDO based on known current consumption.}

\requirement{Buck Converter}
{To reduce power loss from LDO directly - 33\% of power was estimated to be from the LDO alone on V1.}
{Should regulate VEPS to 0.3-0.5V above LDO output i.e., to LDO output voltage. The lower the dropout, the lower the power loss.}

\subsubsubsection{Interfaces}

\requirement{DCMI}
{Needs to receive image data.}
{14-bit - will make it compatible with most DCMI modules.}

\requirement{USB FS}
{Allows me to preview images and efficiently test the board}
{At least FS.}

\requirement{EPS}
{Needs to be powered by EPS}
{Needs to use EPS 4-pin Pico lock connector.}

\requirement{OBC}
{Needs to communicate with OBC}
{Needs to use inverted OBC connector. Communicate over SPI.}

\requirement{C2I}
{Need to be able to connect to camera breakout. Using 5V instead of 3V3. Allows us to isolate the camera power from the rest of the board. Allows us to regulate voltages like 3V8 for the IMX900. Also allows us to characterise the power of the board and sensor individually, increasing the resolution of the power characterisation.}
{Should accommodate full DCMI 14-bit bus, plus 4 GPIOs, and use the 5V from EPS. Doesn't need to match up with CSI bridge, excluding CSI from current scope to reduce complexity.}

\requirement{OBC Connector Fully Connected}
{Allows the UART pins to be configured as GPIOs for miscellaneous use if needed.}
{Connect SPI and UART pins.}

\subsubsubsection{Hardware}

\requirement{HSE}
{For stable clock, no LSE as RTC not used.}
{TCXO for temperature stability.}

\requirement{Less LEDs}
{I found that most LEDs were unused when developing the other boards, as errors would be flagging in the IDE during debug rather than via an LED.}
{Only using strictly required LEDs: 3V3, CD for SD. Use jumpers so they can easily be desoldered to deactivate LEDs, or configure a GPIO pin as the return path (turn on when driven low).}

\subsubsubsection{PCB Layout \& Physical Design}

\requirement{Clear silkscreen}
{Silkscreens on v1.0 did not print properly as they were on the edge of JLC requirements.}
{Slightly larger silkscreen text.}

\requirement{Non-through hole headers}
{Through holes take up a lot of space as they go through each layer. As they won't be used on the CubeSat version, no point allocating so much space for them if they can just be a surface mount component. Frees up space on other layers.}
{Surface mount, 0.1inch.}

\requirement{Mounting holes}
{Needs to be secured to a payload bay and vibration table}
{Coordinate with mechanical for mounting pattern dimensions. Standard 4-corner.}

\requirement{Connector Placement}
{External connectors should be placed where we expect the cables to be to reduce cable length and promote organisation and ease of integration.}
{Connectors should be placed on as few sides as possible. The ideal case is a single edge. If connectors are placed on all sides/edges, it "expands" the actual size of the board, as the new cables sprout outwards from each direction, meaning there's extra cable / wraparound on each edge.}

\subsubsubsection{Debugging}

\requirement{SWD}
{For easy programming and live-debugging.}
{No large header, small to reduce PCB size.}

\requirement{Test Points}
{For logic analyser probing}
{Broken out on all signal lines, small test point only e.g., 2mm pad.}

\requirement{Telemetry Logging}
{Shall be capable of relaying heartbeat statuses to OBC to identify and resolve potential issues.}
{Be capable of checking heartbeats upon request and sending results to OBC. Voltage sensing for 3V3 supplies?}

\requirement{Remote debugging / control}
{In the event of a fault or error, C2S shall be capable of being restarted or corrected to ensure it operates correctly in the future.}
{Have a circuit or system implemented to automatically reset the STM32 upon a specific OBC command e.g., STM32 activates a scheduler component that activates the RESET pin of the STM32.}

\subsubsubsection{Environmental}

\requirement{Temperature}
{Needs to withstand space environment}
{-40 to 85deg}
